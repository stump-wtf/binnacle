# ADR-0003: StumpCloud service discovery from Ansible inventory as a Container enrichment source

## Context and Problem Statement

ADR-0002 defines binnacle's fleet taxonomy as Site → Host → Guest → Container with hardware attachments. Containers are discovered via per-guest Docker probes and enriched with live state (image, status, ports). But Docker alone gives an incomplete picture of what a container *is*: it knows the image tag and running state but not the service's purpose, its DNS name, whether it fronts a database, which Caddy vhost routes to it, or whether it is gated behind OIDC. That metadata lives in exactly one authoritative place — the StumpCloud Ansible inventory (`dub.yaml`, `dtw.yaml`, `pdx.yaml`) and the service playbooks that deploy each container.

binnacle already models containers as leaf nodes under Guests. The question is how to enrich them with the service-layer metadata that Ansible already declares, without creating a second source of truth or coupling binnacle to Ansible's internal structure.

## Decision Drivers

* The Ansible inventory is the single source of truth for what services exist, where they run, and how they are configured. binnacle must consume it, not replicate it.
* Service metadata is structurally different from hardware metrics: it is declarative config, not live telemetry. It changes on deploy, not on a polling cadence.
* The fleet taxonomy spine (Site → Host → Guest → Container) is already correct for services — a service IS a container (or set of containers) running on a guest. No new entity type is needed.
* Credentials declared in Ansible (DB passwords, OIDC secrets, API keys) MUST NOT flow into binnacle. The enrichment is structural, not secret-bearing.
* The enrichment must be safe to fail: if the Ansible inventory is unreachable or malformed, binnacle continues showing Docker-discovered containers with whatever metadata Docker provides. Service metadata is additive, never gating.
* The Ansible inventory format is YAML with Jinja2 templating and Vault lookups. Parsing it raw is fragile; consuming a rendered/exported form is robust.

## Considered Options

* **A. Parse raw Ansible YAML** — read dub.yaml/dtw.yaml/pdx.yaml directly, evaluate Jinja2 templates, resolve Vault lookups
* **B. Ansible exports a service manifest** — a playbook renders the inventory into a credential-free JSON manifest that binnacle consumes as a static file or API endpoint
* **C. Per-service API probing** — binnacle probes each container's well-known endpoints (/healthz, /api/v1, etc.) to infer service type and capabilities
* **D. Manual annotation in binnacle config** — operators declare service metadata in binnacle's own baseline config, duplicating what Ansible already knows

## Decision Outcome

Chosen option: **B. Ansible exports a service manifest**, because it keeps the Ansible inventory as the sole authority, avoids coupling binnacle to Ansible's internal YAML/Jinja2/Vault structure, produces a stable credential-free contract, and fails safely when unavailable.

### Consequences

* Good, because the manifest is generated by Ansible itself — it sees the fully-rendered inventory with all group vars, host vars, and defaults resolved, so binnacle gets the same view an operator sees when running a playbook.
* Good, because credentials are stripped at export time by the playbook that generates the manifest, not by binnacle trying to recognize and redact them. The security boundary is at the source.
* Good, because the manifest is a stable JSON schema that binnacle can version and validate independently of Ansible's internal refactors. Adding a field to the manifest is a deliberate act, not an accidental side effect of an inventory restructure.
* Good, because the enrichment is optional: binnacle loads the manifest at startup and merges it with Docker-discovered containers. If the manifest is missing or stale, containers still appear with Docker metadata alone.
* Bad, because the manifest is a point-in-time snapshot, not live. A service deployed between manifest regenerations appears only as a bare Docker container until the next export. Mitigation: regenerate on every Ansible converge (the natural cadence), and surface staleness in the UI.
* Bad, because it adds a build-time dependency on the Ansible repo. binnacle cannot generate the manifest alone; it needs access to the rendered inventory. Mitigation: the manifest is committed to the binnacle repo or served by a CI artifact, so runtime has no Ansible dependency.

## The Service Manifest Schema

The manifest is a JSON document mapping `(host, container_name)` pairs to service metadata. Each entry carries only structural information — never credentials.

```json
{
  "generated_at": "2026-08-15T12:00:00Z",
  "inventory": "dub.yaml",
  "services": [
    {
      "host": "ie01",
      "guest_vmid": 100,
      "container_name": "cairn",
      "service_name": "cairn",
      "dns": "cairn",
      "image": "gitea.stump.rocks/joestump-agent/cairn:0.0.2-dev.2",
      "port": 8080,
      "enabled": true,
      "caddy_vhost": "cairn.stump.rocks",
      "oidc_gated": true,
      "has_database": true,
      "database_type": "postgres",
      "homepage_group": "Applications",
      "homepage_description": "AI-native artifact sharing",
      "sidecars": ["cairn-docs"],
      "tags": ["feature"]
    }
  ]
}
```

Fields:

| Field | Source | Notes |
|---|---|---|
| host | inventory hostname | Matches ADR-0002 Host key |
| guest_vmid | Proxmox VMID | Links to ADR-0002 Guest identity |
| container_name | service role's `name` | Matches ADR-0002 Container identity |
| service_name | inventory key | Stable across renames of dns/image |
| dns | `dns:` var | The Caddy vhost slug |
| image | `image:` var | Full registry/tag reference |
| port | `port:` var | Internal container port |
| enabled | `enabled:` var | false = tombstoned, container absent |
| caddy_vhost | derived from dns + dns.wtf | null if caddy.enabled is false |
| oidc_gated | oauth2_proxy.enabled or oidc block present | Boolean |
| has_database | db.enabled | Boolean |
| database_type | db.type | postgres, mariadb, or null |
| homepage_group | homepage.group | For UI grouping |
| homepage_description | homepage.description | For UI display |
| sidecars | sidecars keys | Names of companion containers |
| tags | labels matching known patterns | feature, bug, toil, etc. |

## Integration with ADR-0002 Fleet Taxonomy

Service manifest entries merge into the existing Container entities discovered by Docker probes:

1. Docker probe discovers container `cairn` on guest vmid 100 of host `ie01`.
2. Manifest lookup matches on `(host=ie01, container_name=cairn)`.
3. Container entity is enriched with service metadata fields.
4. Unmatched containers render with Docker metadata alone (no error, no warning beyond a visual indicator).
5. Manifest entries with no matching Docker container surface as "expected but not running" — a config drift signal.

The containment spine is unchanged: Site → Host → Guest → Container. Services are not a fifth level; they are attributes of containers.

## Authority Boundary

* **Ansible inventory** is authoritative for: what services exist, their configuration, their intended host/guest placement.
* **Docker probe** is authoritative for: whether a container is actually running, its live resource usage, its uptime.
* **Manifest** is the bridge: a credential-free projection of Ansible's view, consumed by binnacle as enrichment.
* **binnacle** MUST NOT write back to Ansible or modify the manifest. It is a read-only consumer.

## Pros and Cons of the Options

### A. Parse raw Ansible YAML

* Good, because no intermediate artifact.
* Bad, because Jinja2 evaluation requires the full Ansible runtime, Vault tokens, and group_vars resolution. Fragile, tightly coupled, and a credential leak risk.

### B. Ansible exports a service manifest (chosen)

* Good, because clean separation of concerns, credential-free by construction, stable schema.
* Bad, because point-in-time snapshot with regeneration lag.

### C. Per-service API probing

* Good, because discovers live capabilities regardless of config.
* Bad, because slow, unreliable (services may not expose introspection), and cannot determine intent (OIDC gating, DB backing) from HTTP responses alone.

### D. Manual annotation in binnacle config

* Good, because no external dependency.
* Bad, because guaranteed drift — two humans maintaining the same fact in two places. Exactly the duplication ADR-0002's "config declares, discovery describes" principle forbids.

## Confirmation

* A playbook in `stumpcloud/ansible` generates the manifest from the rendered inventory, stripping all credentials.
* binnacle loads the manifest at startup and merges entries into Docker-discovered containers.
* The fleet taxonomy types in `packages/core` gain optional service-metadata fields on Container.
* The UI renders enriched container cards with DNS, OIDC status, and database backing.
* Missing or stale manifests degrade gracefully to Docker-only metadata.
